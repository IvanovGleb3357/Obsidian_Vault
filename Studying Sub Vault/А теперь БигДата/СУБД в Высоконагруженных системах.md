## Проблемы высоких нагрузок
Метрики для измерения нагрузки:
- **rps, rpm** (requests per amount of time)
- **packets per second**, **megabytes per second**
- Количество одновременных соединений (**Simultaneous connections**)
- **Latency** - время, которое проходит от момента отправки запроса до получения ответа
- **Throughput** - пропускная способность системы. Например, сколько писем могут принимать наши сервера
Latency используют чаще, там, где важна скорость и используют перцентиль, например 95 или 99-ый

## Транзакции в СУБД
**Atomicity** - Атомарность. Гарантирует, что либо все операции транзакции будут успешно применены, либо ни одна из операций транзакции не выполниться.
**Consistency** - в реальности означает, только то, что все *constaints* будут выполнятся. Хотя по сути, поддержание согласованности - задача приложения а не базы данных
**Isolation** - свойство которое позволяет выполнять параллельные транзакции как последовательные.
**Durability** - Данные при отдаче ответа зафиксированы в энергонезависимой памяти. Полностью это свойство обеспечить невозможно. Диски сбоят. Но можно повышать гарантии (репликации).

## Репликации часть 1
#### **Зачем**
- Балансировка нагрузки:
	- Много чтения, мало записи
	- Тяжелые запросы (аналитика, отчеты)
	- Бэкапы
- Увеличение надежности
	- Отказоустойчивость
	- Повышение доступности
- Уменьшение латентности
	- Гео-репликация
**Не резервное копирование**
- Если испортить мастер-базу, то реплики тоже испортятся
- Можно использовать отложенную репликацию
**Не масштабирует запись**

#### Виды репликаций по гарантии доставки
	![[Pasted image 20240425184233.png]]
**Синхронная**
	- Ждет подтверждения от реплики, только после этого возвращаем ответ источнику запроса
	- Гарантирует сильную согласованность данных
	- Медленный ответ
**Асинхронная**
	- Отвечаем сразу, подтверждение от реплики приходит позднее
	- Не гарантирует сильную согласованность данных
	- Гарантирует согласованность в конечном счете
	- Быстрый ответ
**Семисинхронная**
	- Дожидаемся подтверждения от реплики о **получении** запроса на запись
	- Отвечаем пользователю после получения подтверждения от всех реплик
	- Не гарантирует сильную согласованность
	- Гарантирует согласованность в конечном счете

#### Виды репликаций по способу передачи данных
**Бинарная** - передача файлов журналов записи. Все что записано на мастер передается на фоловер.
	Нет атомарности
**Логическая** - передача SQL-команд
	Атомарность по SQL-командам
**Триггеры** - для частичной репликации
	Атомарность вплоть до значения одного поля в записи
**По источнику события передачи данных**
	**Push** - лидер сам рассылает данные по репликам
	**Pull** - реплики периодически запрашивают обновления


#### Реплика старт/отказ
1. Загрузка снэпшота базы
2. Запросить все данные, начиная с момента последней записи
3. Записать запрошенные данные
4. Повторять шаги 2-3, пока не догоним лидера
#### Лидер старт/отказ
1. Определить недоступность лидера
2. Выбрать нового лидера
3. Переконфигурация системы для использования нового лидера

#### Типы согласованности
**Strong consistency** - после завершения обновления данных все последующие чтения вернут обновленные данные
**Monotonic read/write consistency** - процесс не может получить старое значение после нового/записать значения не в том порядке
**Weak consistency** - есть окно несогласованности
**Eventual consistency** - согласованность в конечном счете, размер окна несогласованности не фиксирован, зависит от внешних условий
**Casual consistency** - причинная согласованность, только процессы, уведомленные об обновлениях гаранитрованно прочитают новые данные
**Read-your-writes consistency** - только сам процесс гарантированно читает обновленные им самим данные
**Session consistency** - процесс получает доступ к хранилищу в рамках сессии

## Репликация часть 2
#### Проблемы репликаций
1. **Отставание репликации**
	Рекомендации:
		1. Убивать медленные запросы
		2. Держать реплику для медленных запросов
		3. Думать о кросс-СУБД репликации
		4. Стараться избегать паттерна запись-чтение (запись на мастер, а чтение слейв)
2. **Чтение своих записией**
	Рекомендации:
		1. Свои данные читаем с мастера, чужие с реплики
		2. Читам с мастера n секунд после записи
3. **Монотонное чтение**
	Чтение может происходить с разных реплик, поэтому данные могут разниться. Решение - пользователя привязываем к определенное реплике
4. **Согласованное префиксное чтение**
	Характерно для шардированных баз данных, когда на каждом шарде свой мастер, но запись которая является следсствием, записалась раньше причины. И тогда если читать их, то будут не в том порядке.

**Global transaction identifier** (GTID) - состоит из server-id:transaction-id. Позволяет убедиться, что транзакция принадлежит только одному серверу и применена только один раз в системе.

#### Проблемы master-master репликации
ВАЖНО - мастер-мастер не масштабирует запись. Для этого применяется шардирование!
**Варианты применения**
	1. Географическая распределенность (в каждой стране, например)
	2. Hot-standby Реплика
	3. Offline клиенты. Например покупки с карты в самолете или в глухой деревне. 
**Варианты решения конфликтов**
	1. Избегание конфликтов (запись каждого изменения с id мастера)
	2. Last wins (сложно синхронизировать время)
	3. Ранг реплик. Выигрывает запись от старшей реплики
	4. Слияние
	5. Решение конфликтов на клиенте
	6. Conflict-free replicated data types (CRDT) - использование дельты, а не четкого значения
	7. Meargeable persistent data structures - корзина озон, мама добавляет товары в корзину с ноутбука, а папа с компьютера. Затем происходит просто объединение.

## Шардирование
При шардирование данные живут на разных серверах, в отличии от партиционирования.
**Помогает**:
	1. Горизонтальное масштабирование
	2. Ускорить обработку запросов (особенно запись!)
	3. Повысить отказоустойочивость (часть данных отрыгнет всего лишь)
**Как можно шардить**
	1. Key Based Sharding. К ключу применяем хэш-функцию
		**Плюсы** - Просто и понятно, равномерное распределение
		**Минусы** - добавление / удаление шарда всегда боль, т.к. алгоритм шардирования обычно завязан на количестве шард. Поэтому необходимо потом делать решардинг.
	2. Range Based Sharding. По рэнджу шардируем лол
		**Плюсы** - прост в реализации
		**Минусы** - потенциально неравномерная нагрузка, обновление
	3. Directory Based Sharding. Похож на range based, применим к категориальным переменным.

**Как находить шарды?**
1. Из приложения (умный клиент)
	Нет асбтракции, реализация в коде
2. Прокси (прослойка)
	Лишняя точка отказа
3. Координатор (аналог нейм ноды в hadoop)
	Приложение не знает о шардинге, код не меняется. Лишняя точка отказа

**Проблемы шардинга**
1. Плохо распределили данные
	Подобрать лучший ключ/функцию шардирования
2. JOIN-s
	Держать данные на одной машине, джоин по ключу шардирования
3. Решардинг
	Количество шардов - степень 2йки
