Виды интеграций:
1. Нет интеграции между системами. Задачи по передаче информации между системами переносятся на конечных пользователей. Риски - **Человеческий фактор** и как следствие **Потеря данных**.
										![[Pasted image 20240212091855.png]]
2. Вертикальная интеграция. Объединение в единый тех процесс всех или основных звеньев производства и обращения, создание холиднга с одной инфраструктурой, с едиными бизнес- процессами, техонлогиями, компетенциями. Главенствие одной системы
										![[Pasted image 20240212092227.png]]
3. Горизонтальная интеграция. Хранение функций приложений, подключенных к шине, и обеспечение возможности использования этих функций другими приложениями, также подкюченными к этой шине
										![[Pasted image 20240212091832.png]]
4. Интеграция "многие ко многим" звезда. Каждая из используемых систем может при необходимости обращаться к функциям любой другой системы.
										![[Pasted image 20240212092007.png]]
5. Отсутствие необходимости в интеграции. Системы или модули системы работают автономно друг от друга.
										![[Pasted image 20240212092130.png]]

**Интеграция платформ**
	1. Взаимодействие между приложениями, работающими на различных программно-аппаратных платформах.
	2. Работа приложений, разработанных для одной программно-аппаратной платформы, на других программно аппаратных платформах
	Решение:
		1. Удаленный вызов процедур
		2. ПО промежуточного слоя
		3. Виртуализация (Виртуальные машины)

**Интеграция данных**
	Совместное использование данных различных систем
	Решение:
		1. Универсальный доступ к данным
		2. Хранилища данных

**Интеграция приложений**
	Использование готовых функций приложений другими приложениями
	Решения:
		1. Интерфейсы прикладного программирования
		2. Обмен сообщениями
		3. Сервис-ориентированная архитектура
		4. Интеграция пользовательских интерфейсов

**Интеграция бизнес-процессов**
	Интеграция приложений, и интеграция данных и, что не менее важноо, людей, вовлеченных в этот бизнес-процесс
	
**Виды взаимодействия**
	![[Pasted image 20240212103448.png]]
1. Синхронное взаимодействие - взаимодействие между компонентами, при котором клиент, отослав запрос блокируется и может продолжнать работу только после получения ответа от сервера. По этой причине такой вид взаимодействия называют иногда блокирующим.
2. Асинхронное взаимодействие - взаимодействие между компонентами, при котором клиент, отослав запросЮ не блокируется и может продолжать работу не дожидаясь получения ответа от сервера. Клиент периодически опрашивает состояние обработки запроса.
3. Реактивное взаимодействие - вид асинхронного взаимодействия, при котором сервер вызывает функцию обратного вызова (call back) или отправляет сообщение о результате обработки заданному в исходном запросе адресату.
## **Способы интеграции
Категории API
1. Open API - публичное использование
2. Internal API - внутри компании
3. Partner API - партнерами

**Синхронные**:
 1. Web-сервисы (API)
	 Синхронные HTTP-запросы используются для обмена данными между системами. RESTful API является часто используемым примером синхронной интеграции
2. SOAP (Simple Object Access Protocol)
	 Протокол, основанный на XML, часто используемый для синхронной интеграции между веб-службами.
3. RPC (Remote Procedure Call)
	Синхронный метод вызова удаленных процедур, где клиент ожидает ответа от сервера.
4. GraphQL
	Язык запросов для API, которые позволят запрашивать клиентам только те данные, который им нужны.
5. База данных
	1. прямое подключение к БД
	2. удаленный вызов процедур
	3. DB-Link

**Асинхронные**:
1. Промежуточное ПО - Брокеры сообщений, Шины
	Используются для асинхронной передачи сообщений между компонентами системы. Примеры включают RabbitMQ, Apache Kafka.
2. EDA (Event-Driven Architecture)
	Системы, где компоненты реагируют на события, передаваемые в асинхронном режиме. Примеры включают в себя использование брокеров событий.
3. FTP (File Transfer Protocol)
	Асинхронный протокол передачи файлов, где файлы могут быть загружены и скачены в асинхронном режиме.
4. Веб-сокеты, веб-хуки
	Механизм, позволяющий веб-приложению отправлять HTTP-запросы другим приложениям в асинхронном режиме при наступлении определенных событий.

**Протоколы передачи данных** - набор соглашений, который определяет обмен дыннх между различными программами. Протоколы задают способы передачи сообщений и обработки ошибок в сети, а также позволяют разрабатывать стандраты, не привязанные к конкретной аппаратной платформе
1. Модель OSI
	1. Физический (сигналы)
	2. канальный (LLC/MAC)
	3. Сетевой (ARP)
	4. Транспортный (TCP/UPD)
	5. Сеансовый (сессии, сеансы)
	6. Представления (преобразование)
	7. приложения (HTTP/FTP/SMTP)
2. Модель TCP/IP
	1. канальный (Ethernet/ Token Ring)
	2. сетевой (IP)
	3. транспортный (TCP/UDP/SCTP/DCCP)
	4. прикладной (HTTP/RTSP/FTP/DNS)

## REST
Rest API - архитектурный стиль, который говорит как наиболее эффективно общаться клиенту с сервером по HTTP. 

**RESTful 7 принципов**:
1. Модель взаимодействия **клиент-сервер**. API представленна в виде сервера, а потребителем является как мобильные так и десктопные, браузерные приложения.
2. Система может быть **многоуровневой**. Сервера могут располагаться на разных уровнях, при этом каждый сервер взаимодействует только с ближайшими уровнями и не связан запросами с другими.
						![[Pasted image 20240112185836.png]]
3. **Stateless** - отсутствие запоминания состояния клиента. Поэтому клиент должен предоставлять всю необходимую информацию, чтобы сервер мог ее выполнить. Клиент и сервер общаются каждый раз как в первый раз.
4. Единообразный **унифицированный** интерфейс. Допустим у нас есть интернет магазин. Над любыми сущностями мы можем CRUD (create, read, update, delete) - операции
5. **Кеширование**.  GET и POST - могут кешироваться. PUT и DELETE не кешируются. Допустим у нас есть сервер со списком валют. Юзеры отправляют гет запрос. Список валют меняется редко, поэтому нет смысла каждый раз выполнять этот запрос. Поэтому на диаграмму добавляется кэш, который хранится или в бразуере или на стороннем сервере.
						![[Pasted image 20240112192951.png]]
6. Формат обмена данными. JSON и XML.
						![[Pasted image 20240112193245.png]]
7. **Версионирование**. Все правки которые мы вносим, дольжны быть обратносовсместимы.	
						![[Pasted image 20240112193346.png]]
8. **Код по запросу**. Серверы могут отправлять клиенту код. Так общий код приложения или сайта становится сложнее только при необходимости.

## SOAP(Simple Object Access Protocol) VS REST (Representational State Transfer)
REST и SOAP на самом деле не сопоставимы: REST - архитектурный стиль. SOAP - формат обмена сообщениями. REST - передача состояния представления. SOAP - бюрократический свод правил, про коды состояний.
						![[Pasted image 20240113191302.png]]
Специфика **SOAP** - всегда SOAP-XML, которы представляет собой XML, включающий:
				![[Pasted image 20240113191141.png]]
				**ENVELOPE** - Отвечает за начало и конец
				**HEADER** - Заголовок, указать доп информацию для него можно
				**BODY** - полезные данные
SOAP испльзоует WSDL - язык программирования.
Протокол обмена структурированными сообщениями
					![[Pasted image 20240113190849.png]]

**Формат обмена сообщениями**:
В SOAP - SOAP-XML
В REST - нет фиксированного формата, обычно XML, JSON.

**Опеределение услуг**:
В SOAP - WSDL (Web Services Description Language) - язык описания веб-сервисов и доступа к ним, основан на XML
В REST - нет стандарта, в основном используется Swagger, OpenAPI

**Транспорт**
SOAP не накладывает никаких ограничеий на тип транспортного протокола. Можно использовать либо Web протокол HTTP, либо любые другие (FTP, SMTP).
REST подразумевает наилучшее использование транспортного протокола HTTP, HTTPS

**Простота реализации**
RESTful веб-сервисы как правило, гораздо прозе реализовать, чем веб-сервисы на основе SOAP
	REST использует JSON, который легче анализировать и обрабатывать. Также REST не требует наличия определения службы для предоставления веб-службы.
	В случае SOAP необходимо определить свой сервис с использованием WSDL и при обработке и анализе сообщений SOAP-XML возникают большие накладные расходы.

**SOAP - stateful, а REST - stateless**
