## Модель преставления архитектуры **4+1**:

Включает в себя 4 типа представления:
	1. Логическое представление - Логика - Что?
	Диаграмма классов, последовательности. Функциональные требования. Схема базы данных.
	2. Представление реализации - Как?
	Диаграмма компонентов, пакетов.
	3. Процессное представление
	Все процессы и свзяи. UML -лиаграмма активностей.
	4. Физическое представление
	Как элементы системы физические (сервера там) функционируют между собой.
	5. Сценарии использования

**Эволюция архитектуры**:
1. Одноуровневая архитектура. Клиент
	1. Нет граф. интерефейса
	2. Не мсштабируется
2. Двухуровневая архитектура (клиент-серверная архитектура). Клиент - БД
	1. Разделение ответсвенности между UI и обработкой
	2. Более простое обновление (**толстый клиент** - делает на своих возможностях)
3. Трехуровневая архитектура. Клиент - Сервер - БД
	1. Высокая степень гибкости
	2. В качестве клиента - браузер (**тонкий клиент** - применяет ПО центрального сервера)

## Виды Архитектуры
1. **EDA** - Событийно ориентированная система
	Архитектурный подход, при котором компоненты системы взаимодействую событиями, отправляя и принимая уведомления о событиях, что позволяет реагировать на изменения в реальном времени.
	**Преимущества**
		- Отзывчивость. Система реагирует многовенно на изменения.
		- Легкость масштабирования. Компоненты могут быть доабвлены или удалено с минимальными изменения самой системы.
		- Гибкость. Позволяет легко вносить изменения в систему.
		- Позволяет обрабатывать события асинхронно
	**Недостатки**
		- Сложность отладки и мониторинга. Из-за асинхронности.
		- Сложность управления состоянием из-за асинхронности.
		- Сложность обеспечения согласованности.
		- Потенциальная сложность обработки ошибок.
2. **SOA** - Сервис Ориентированая Архитектура (Манифест)
Похожа на микросервисы, однако в микросервисах максимальная декомпозиция бизнес-логики (один сенврис - одна функциональность) - можно дублировать сервисы. В СОА единая база данных, в МСА несколько БД (для каждого сервиса своя), в SOA испльзуется шина.
3. **Микросервисы** - один сервис, одна задача
4. **CLOUD** - SaaS, PaaS, IaaS
5. **SERVERLESS** - бессервенные вычисления
### **Монолит VS Микросервисы**
**Монолит**:
	**Плюсы**:
		- Легко разрабатывать, доробатывать, разворачивать, отслеживать ошибка, просто масштабировать.
	**Недостатки**:
		- А потом, сложно делать все, как монолит вырастает.
1. Подходит для запуска MVP
2. Для небольшой команды
3. Нет архитектора для реализации сложной структуры
4. Маленькое приожение, где нет богатой бизнес-логики

**Микросервис**:
	**Плюсы**:
		- Возможность управлять кол-во экземпляров определенно сервиса
		- Простота развертывания
		- Устойчивость к сбоям
		- Возможны эксперементы с новыми технологиями
		- Маленькие команды = более эффективный менеджмент
		- Независимость модели данных
	**Недостатки**:
		- Сложность решения
		- Скорость работы (интеграции)
		- Чаще подвержены сбоям
		- Необходимость культурных изменений (мониторинг, devops)
		- Данные будут согласованы когда-нибудь (несогласованность данных)
		- Высокая стоимость

**Как перейти от монолита к микросервису?**
1) Новый сервис с:
	1) сложной логикой
	2) высокой нагрузкой
	3) Для него будет отдельная команда
2) Имеющийся сервис:
	1) часто модифицируется
	2) есть огромное желание, как можно быстрее го релизить
	3) он должен быть безотказным (не падать)
Шаги:
		1. Проанализировать все связи с монолитом
		2. Описать логику микросервиса
		3. Проработать интеграцию нового микросервиса с монолитом
		4. Проработать вопросы мониторинга и логирования
		5. Проработать вопросы с командой по постепенному переключению трафика с монолита на микросервис
		6. Проработать список критических ошибок, при выявлении которых вы переключите трафик на ваш монолит

## ООП
Есть классы и объекты. **Класс** - шаблон код. **Объект** - экзепляр класса. 

**Основные принципы ООП**:
1. **Инкапсуляция**.  Это ограничение доступа к данным класса, скрывая детали реализации от пользователя. В Python это достигается с помощью приватных атрибутов и методов, которые обозначаются двойным подчеркиванием. Предоставлять методы работы с избранной музыкой, но не с ней самой.
						![[Pasted image 20240305101156.png]]
2. **Полиморфизм**. В программировании это означает, что один интерфейс может использоваться для управления разными методами, давая разные результаты в зависимости от контекста. Часы, телефон, колонка - выключить свет.
						![[Pasted image 20240305101354.png]]
3. **Абстракция**. Абстракция позволяет скрыть сложные детали реализации и показать только необходимые аспекты объекта пользователю. Также они позволяют явно указать, какие методы должны быть реализованы в классах-потомках.
						![[Pasted image 20240305101653.png]]
4. **Наследование**. Способность объекта или класса базироваться на другом объекте или классе. Это главный механизм для повторного использования кода. Наследственное отношение классов четко определяет их иерархию.
