

## UML
UML - UNIFIED MODELING LANGUAGE - это система обозначений, которую можно применять для объектно-ориентированного анализа и проектирования. Его можно использовать для визуализации, спецификации, конструирования и документирования программных систем.

Типы диаграмм:
- Структурные
	- Диаграмма классов. Отображает структуру системы, содержащей различные объекты и классы. Чаще всего используется, чтобы продемонстрировать иерархию классов внутри программы.![[Pasted image 20231123104202.png]]
	- Диаграмма компонентов. Описывает компоненты ПО и их связи между собой. Например, как микросервисы взаимодействуют друг с другом.![[Pasted image 20231123104333.png]]
	- Диаграмма объектов. Показывает, как компоненты системы выглядят в определённый момент времени. Позволяет смоделировать объекты системы и связи между ними.![[Pasted image 20231123104445.png]]
- Поведенческие диаграма
	- Диаграмма действий. Показывает последовательность действий, варианты решений и их результаты.![[Pasted image 20231123104553.png]]
	- Диаграмма сценариев использования. В ней обычно изображают пользователей, «агентов», которые взаимодействуют с системой. Эту диаграмму используют для определения функций ПО и связи сценариев использования, то есть [юзкейсов](https://practicum.yandex.ru/blog/chto-takoe-use-case-kak-ih-napisat/), друг с другом. По ней определяют, какие возможности есть у разных групп пользователей и как системы участвуют в выполнении юзкейса.![[Pasted image 20231123104651.png]]
	- Диаграмма последовательностей. Изображает последовательные действия во времени, которые иногда называют сценариями.![[Pasted image 20231123104724.png]]

## ER диаграмма
ER диаграмма - entity relationship diagramm - Собрав все сущности будущего проекта, системный аналитик выясняет, как они связаны между собой, и составляет ER-модель (сокр. от entity–relationship модель или модель «сущность-связь»).
Типы связей:
● **«Один-к-одному»** — один экземпляр сущности связан только с одним экземпляром другой сущности. Например, пассажир рейса и его место в самолете. 
● **«Один-ко-многим»** — один экземпляр сущности связан со множеством экземпляров другой сущности. Например, у одного пассажира может быть несколько единиц багажа, при этом каждая единица багажа может быть связана только с одним пассажиром.  
● **«Многие-ко-многим»** — множество экземпляров одной сущности связаны со множеством экземпляров другой сущности. Например, аэропорт обслуживает несколько авиакомпаний. При этом каждая авиакомпания может обслуживаться в нескольких аэропортах.

### Требования
Уровни требований:
- Верхний уровень - бизнес требования. Пример: 
	Система должна сократить срок оборачиваемости обрабатываемых на преприятии заказов в три раза.
- Средний уровени - уровень требований пользователя
	Система должна представлять диалоговые средства для ввода имчерпывающей инофрмации о заказае, последующей фиксации информации в базе данных и маршрутизации информации о заказе к сотруднику, отвечающему за его планирование и исполнение.
- Нижний уровень - функциональный. 
	Пример: Заказ может быть создан отредактирован, удален и перемещен с участка на участок.

Верификация - соответствие спецификации
Валидация - соответствие потребностям пользователя
